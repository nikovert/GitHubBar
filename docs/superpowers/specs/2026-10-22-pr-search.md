# Pull request search

## Requested outcome

Search pull requests by title, description, changed file paths, and changed code.
Results have two sections, always in this order:

1. **In your list**: matches in the current Active workload.
2. **Extended results**: other matching PRs, without duplicating the first section.

Show the title, repository and number, author, open/merged/closed state, and a
short matching excerpt with its source (Title, Description, File, or Code).
Opening a result goes to its GitHub PR; a code result also offers Files changed.
This does not add a review request, launch an agent, or modify a PR.

## Proposed scope and interaction

Builder choices, not additional requests from the user:

- A Search PRs action near the top of the native status menu opens a reusable
  native search window. Command-F in the app opens/focuses it. A separate window
  avoids making native NSMenu tracking responsible for a live text editor.
- Search the Active workload first. An explicit Extended search toggle adds
  the second section. Keep the two headings visible with useful empty states.
- Extended search includes open, merged, closed, and draft PRs. Its repository
  selector defaults to the app's pinned repositories when Pinned is active;
  otherwise it defaults to repositories represented in the Account workload.
  The user can add another accessible owner/repository explicitly. All PRs means
  all PRs in the visibly listed search repositories, not all public GitHub.
- Search literal, case-insensitive words and code identifiers locally, with
  word-coverage and exact-phrase boosts. Titles rank above descriptions, then
  paths, then diff text; recent activity breaks ties. It is not an LLM/semantic
  search and does not send code to a third-party service.
- Whitespace separates terms; preserve punctuation within identifiers and paths.
  Match any term, rank more matched terms higher, and treat a quoted phrase as
  one literal term. Available context lines count as code but are labeled Context
  rather than Added or Removed. Show the matching line and path.
- A result in the first section always precedes every extended result, even
  if an extended result has a higher text score. Membership is by canonical
  repository identity and PR number, not title or author.

## Fetching changed code honestly

GitHub issue/PR search supports title/body/comments, not arbitrary diff content.
Do not filter candidate PRs by title/body and then claim their diffs constitute
an exhaustive code search: that misses PRs whose only match is in changed code.

Build a local, account-bound index incrementally. Fetch current-list descriptions
and diffs first. For each extended repository, enumerate all PRs through paginated
repository PR APIs, including closed/merged PRs, rather than relying on a capped
global search. Stream results while indexing. Show discovered/indexed counts,
last refresh time, and whether more history remains. Initial history indexing can
take time and use GitHub quota; Pause/Resume and cancellation must work.

Index added and removed lines and available hunk context, plus current and previous
file paths. Do not fetch whole unchanged files, binaries, or run repository code.
The PR-files endpoint has a 3,000-file ceiling and can omit patch text. Track file
list completeness separately from code coverage. Missing or truncated patches,
network errors, local size limits, or rate limits mean partial coverage, never a
confident "no matches" for unsearched code. Explain affected PR coverage in the UI.

Persist the index and scan progress locally, keyed by GitHub hostname, account,
repository identity, PR number, base SHA, and head SHA. Refresh metadata and detect
head/base changes before reusing a diff as current. Interrupted scans resume and
upsert idempotently. A freshness refresh must detect newly created PRs as well as
edits to older PRs; pagination order and snapshot boundaries must be tested.

Use bounded background requests, GitHub rate-limit backoff, and a bounded local
storage policy. Keep at most 1 GiB of reusable diff-cache data, evicting old diffs
but retaining discovery metadata. Extended searches stream through uncached PRs
for the submitted query and retain matching snippets separately, so cache eviction
does not cause an endless rebuild or remove already-found results. A new query may
need to rescan evicted history; state this explicitly. Paginate results without a
silent top-N ceiling. The SQLite database may grow with metadata and actual matches;
low disk space pauses the scan visibly and never discards current results silently.
Keep the
normal workload refresh usable and prevent search from consuming its remaining
quota. No indexing starts merely because the status menu opens or scope changes.
Typing searches cached data; Return/Search submits the extended scan. Closing the
window, turning Extended off, or exiting the app pauses network work. Resume is
explicit after reopening/restarting; preserve the submitted query and checkpoints.

Check the PR's revision identity before and after paginated file retrieval; discard
mixed-revision responses. Patch coverage remains partial when line counts or file
counts do not reconcile, or completeness cannot be established. Record discovery
scan boundaries and timestamps rather than claiming a live, immutable snapshot.

## Architecture and privacy

Keep the existing WorkloadEngine and its account-wide reconciliation unchanged.
Add an actor-owned PR search engine to GitHubBarCore, with narrow injectable API,
index-store, and clock seams. SwiftUI observes a main-actor search presentation
adapter; it does not own networking, authentication, or indexing orchestration.
This preserves the separation in ADR-0003 while adding a distinct search workload.

Reuse AccountConnection to resolve and verify the explicitly monitored account.
Tokens stay in memory. Use native HTTPS requests to GitHub with that exact token;
never silently use whichever gh account is currently active. Account disconnect
or change cancels requests and removes old results immediately. Guard late results
and persistence writes by account/query generation. Repository removal cancels its
scan and removes its results. Distinguish throttling from access failures: 403 with
rate-limit evidence pauses fetching, while confirmed or ambiguous authorization
failure suppresses private cached results until revalidated. Use an ephemeral HTTP
session with no persistent URL cache. Do not display historical private-cache
results offline in the first version; current workload behavior remains unchanged.

Use SQLite on macOS for indexed text, metadata, and scan checkpoints, without a
new third-party dependency. Store private content only under this account's local
Application Support cache, with private directory/file permissions including SQLite
sidecars. Provide Clear search cache. Never log descriptions, code, or tokens.
Exclude the cache directory from backups; this is not application-level encryption.
Purge the previous search cache on account switch or explicit disconnect, and purge
a repository's cached code and results on explicit removal from search. Clear cache
cancels scans before deletion. Tests must cover SQLite sidecar cleanup and late
network responses so purged content does not reappear.

## Acceptance checks

- A current-list match is first even when an extended result scores higher.
- A PR found through both sources appears only once, in In your list.
- Title-only, description-only, path-only, and diff-only queries all return matches.
- Removed code and renamed file paths are searchable; binary content is not.
- Extended discovery includes open, draft, closed, and merged PRs beyond page one.
- Empty query does not start history indexing; explicit extension starts it.
- First-run/incomplete/paused/rate-limited searches report coverage accurately.
- Query/account/repository changes prevent obsolete responses reappearing.
- Cache restart resumes progress; SHA changes invalidate old code; clear-cache
  prevents in-flight work from silently repopulating cleared data.
- Existing workload, review controls, and terminal-session actions still work.
- Light/dark appearance, keyboard focus, result opening, long text, and empty/error
  states are verified in the Mac app. No live PR writes occur in tests.
